# Financial integrity report (code changes **not execution-verified**; see TEST_REPORT.md)

## F-01 Investor investment (InvestorInvestmentController::store → `investFromWalletAtomically`)
Early pre-checks remain as a fast, *unlocked* reject only. Authoritative path: `DB::transaction` → `User … lockForUpdate()` → plan re-read (limits/terms at commit time) → `Decimal` compare of the **re-read** balance → create position (same snapshot fields: profit %, expected profit, total return, dates, remaining days) → `UPDATE … WHERE balance >= amount` decrement; 0 rows ⇒ exception ⇒ everything rolls back. Failures are 422 with the previous message. Ledger-enabled branch (`InvestmentAllocationService`) was already transactional and is wrapped only for idempotency + the same 422 shape. Duplicate submission: optional `Idempotency-Key` (8–64 `[A-Za-z0-9_-]`), marker via `Cache::add`, released on failure; needs a shared cache store in production. The row lock — not the key — is what prevents overspend.

## F-02 Deposit double representation — design and controlled plan
**Finding (unchanged):** with `financial.separate_deposit_approval=false`, `AdminDepositController::approve` credits the full deposit to wallet cash *and* creates an active investment (`source_deposit_id`) for the same amount without a wallet debit.
**What exists and is retained:** with the flags ON the approval credits `cleared_wallet_funds` only; the investor later allocates cash through `InvestmentAllocationService` (wallet debit + position + `investment_allocations` link, unique keys, one transaction); principal redemption is position-specific (account-level fallback `financial.account_level_redemption_fallback` stays unapproved/off); ledger classifications distinguish wallet cash, allocated principal, profit credit, pending/approved withdrawals, returned principal, historical deposits.
**What this change adds (no balance/investment/ledger row is altered):**
1. `php artisan ssi:reconcile-legacy-deposits [--out=… --user=ID]` — **read-only** CSV of every approved legacy deposit that opened a position without allocation: deposit, position, status, current wallet, active legacy principal, `potential_overlap = min(wallet, active legacy principal)` (a ceiling, not a proven loss), approved-withdrawal total, classification `LEGACY_DUAL_ACTIVE_REVIEW` / `LEGACY_DUAL_CLOSED_HISTORICAL`.
2. `database/controlled/F02_unique_source_deposit.sql` — duplicate check (must return 0 rows) then reversible unique index; **not a migration, not run**.
3. Tests: duplicate approval credits/invests once; legacy behaviour *characterised* (not changed); separated flow classification/ledger links.
**Controlled cutover plan (requires written Management + Financial Team approval at each gate):**
G0 Backup + sanitised staging copy. G1 Run reconciliation on staging; Finance reviews every `ACTIVE_REVIEW` row and records a per-account decision (D1). G2 Stop legacy approvals (queue freeze) → enable `ledger_enabled` then `separate_deposit_approval` on staging; run the Rank + Financial suites and MySQL suite. G3 Parallel-run on staging with synthetic deposits. G4 Production: same sequence in a maintenance window, flags changed by Finance sign-off only; **no automatic balance migration**; any per-account correction is a separate compensating, audited adjustment (BalanceAdjustment + second approval) authorised in writing. G5 Apply unique index (D2) after step‑1 query = 0. Rollback: flags back OFF (historical ledger rows preserved; they are append-only).
**Known limitation:** until cutover, a legacy-approved investor can withdraw cash that mirrors active principal. A legacy-mode withdrawal guard was **not** built because it would change live payout behaviour without D1.

## F-03 / F-14 balance tools
`BalanceAdjustmentService` is the single implementation (AdminUserController, bulk, FinancialInvestorController call it). Per account: transaction, `lockForUpdate`, re-read, decimal, relative `increment/decrement`, `BalanceAdjustment` (admin = requester, reason, before, after, timestamp, approval id, approver) + `FinancialAuditLog` in the same transaction; `UNIQUE idempotency_key` namespaced per user. Bulk: preview endpoint (`preview=true`), ids locked ascending, atomic over all changed accounts, skipped accounts (`zero_delta`, `insufficient_balance`) **reported not hidden**, cap `bulk_max_accounts`, second approval by default. Approval service: approver ≠ requester (hard), configurable role list, single decision, payload hash check, execution in its own transaction, `failed` status on error.
**Role matrix as implemented:** `/api/admin/*` admin only; `/api/financial/*` financial **and admin** (unchanged); approvals inbox financial+admin, decision rights per `approver_roles`; marvflow/investor 403. Financial-only vs admin-only vs dual per action is **not** re-partitioned beyond this (D3/D4).

## F-04 profit adjustment
Preview → request (202) → second approver → `ProfitAdjustmentService::apply`: transaction, ascending row locks on active investments only, status re-check, decimal (`profit_percentage` floor 0, expected = amount × % half-up, total = amount + expected), one `profit_adjustment_items` row per investment (before & after), aggregate row with admin, approver, reason, `authorization_reference`, timestamp; audit log. Reversal restores before-values only where the investment is still active **and** still holds the written values; conflicts are returned, never overwritten; adjustment becomes `reversed` / `partially_reversed`. Rank evaluation, benefit activation and schedulers never call it (test written).

## F-13 / settlement & FX arithmetic
`InvestmentSettlementService`: profit string-decimal through `increment`. `DepositPaymentService`: USD value = `Decimal::mulHalfUp(paid, rate)`; validation already rejects non-USD payments without a positive rate (no default of 1). Original currency, amount, rate, source and timestamps are persisted by the existing code (`rate_source`, `rate_date`, `FxConversionSnapshot`).
